Inside one installation

Every machine uses the same application. The local device role determines whether business commands execute locally or travel to the master. The renderer has no direct filesystem or Node.js access.

The order lifecycle

Draft in renderer→Validate and save→In progress→Completed + stock deduction

Auto-complete skips the preparation state. Completed-order edits calculate the difference between recorded consumption before and after the edit; cancellation restores recorded consumption. The order snapshots names, unit prices, recipes, fees and tax so future catalog changes cannot silently rewrite a historical sale.

1 · Intent

A staff action

The renderer submits a typed command. Order edits include the expected order revision. Administrative commands require an unlocked local session.

2 · Authority

One accepted state

The standalone store or master validates the request, rejects stale writes, applies calculations and persists the resulting state.

3 · Distribution

Every screen catches up

The renderer receives an updated snapshot. Connected clients refresh from the master. Disconnected clients cannot commit business changes.

Data ownership and recovery

Business data is shared: catalog, stock, orders, configuration and inventory movements. Device settings and password hashes stay local. Connected client administrator sessions are authorized by the master’s password and scoped to that client. The master’s business state overrides the client’s replica when connected. Only the master or standalone installation imports manually edited menu files. Other files are application-managed.

JSON is deliberately human-readable. Updates spanning orders and inventory use a transaction/recovery mechanism so a restart can finish a partially written state. External menu edits pass the same schema checks before they become visible; malformed edits do not replace the last accepted in-memory state.

Durability has a boundary.

Transaction recovery protects the application’s write sequence. It does not replace backups, protect against disk failure, or turn local files into a tamper-proof financial record. Use the backup tools and protect Windows access.

Build and distribution

Public pull requests and repository pushes run on GitHub-hosted Windows runners with read-only repository contents permission. Checkout credentials are not persisted. The packaging scripts explicitly disable publishing and the workflow uploads the installer to Actions artifact storage. Release publication is a separate future trust boundary: only a trusted release job should receive repository write permission and a temporary publishing token. No release token is required to build or test the application.

Webpack compiles the TypeScript main process, preload bridge and React renderer. Electron Builder packages the resulting application and produces an NSIS installer for Windows x64. The installer creates Start menu and desktop shortcuts and installs per machine. Runtime data is created on first launch under the actual Windows user’s profile, avoiding data creation in an elevated installer account.

The packaged help document and its stylesheet are copied into the build. This architecture document, implementation notes, acceptance mapping, original brief and sales sheet remain in the source repository. The standalone application does not load remote web assets to render its interface.
